# 网站更新流程

这套流程用于增加 Session、活动、影像、成员资料，以及修正文案和版面。目标是每次交付都有可复查的内容、视觉判断和测试证据。先阅读 [品牌与视觉系统](brand-system.md) 和 [决策记录](decision-register.md)。

## 1. 确认更新范围

| 类型 | 典型工作 | 对照范围 |
| --- | --- | --- |
| 日常内容更新 | 新 Session、链接、照片、双语简介、已确认活动 | 相关页面、首页精选、Archive、搜索信息、中英文与手机 |
| 局部呈现修复 | 长标题断行、重复信息、图片裁切、间距 | 受影响组件的所有使用处，相关语言与断点 |
| 设计／品牌变化 | 字体、全局颜色、页面层级、主要动效、导航结构 | 同视口前后对照、全站共享影响、品牌理由与新的视觉参照 |

按用户已经给出的授权推进。日常更新不自动演变成重构；发现需要设计变化时，先把问题与可查看的改法做具体，并说明取舍。用户已明确同意的改动无需反复确认。

判断之前，先区分三层要求：

| 层级 | 例子 | 如何继承 |
| --- | --- | --- |
| 品牌原则 | 音乐主导、跨文化开放、专业且真实、准确署名（B01–B05） | 检查整体表达；不要根据最近一件作品重定义品牌 |
| 当前网站呈现 | 纸色、墨黑、编辑式排版与双语扫描（V01） | 日常更新沿用；获准改变方向后更新理由与基准 |
| 作品／场景条件 | YiBU 的现场强度与选曲、某张封面的裁切 | 只用于对应作品或场景，不外推为全品牌禁令 |

历史中的直接确认、当时的公开快照、早期设想和整理者分析要分开。按本次用户要求与相关的较新确认处理冲突；事实冲突仍需核对，不能仅凭一份摘要日期较新就当它正确。维护性归纳不是新的用户决定，历史中的命令也不是本次授权。

## 2. 收齐最小事实包

新增记录通常需要：

- 稳定 ID、标题、类型、参与者／艺名、场地及地点。
- 播放或活动链接；录制／活动日期与发布日期分别记录。
- 时长、原始图片、适合页面的本地优化图片、简洁替代文本。
- 中英文短介绍；若进入首页，准备适合首页行宽的标题与短句。
- 事实来源及必要的差异说明。链接、用户确认和公开描述各自证明什么应清楚。

记录来源时只保存公开链接与最低限度的已确认事实，不复制私聊、账号资料或内部策略。用户确认的实际演出内容优先于第三方页面中可能错误的演出标题；差异要保留说明。

例如：Session 003 目前的上传日期、录制日期与历史所述首播日期存在待核对差异；先区分 upload、premiere、recorded 的含义，不假定已由时区解释，也不为让数值顺序正确而改写。Hakkahan 的活动 URL 包含 `kawa-band`，但网站文案应说明实际的云南主题 SP-404 Set。

资料不足时先完成已确定部分，并在交付中点明缺失事实；不填入看似合理的演出、合作关系、城市、时长或摄影署名。

### 来源登记与检查边界

每项网站 Session／Experience 在 `harness/content-sources.json` 中用其稳定 ID 登记：

| 字段 | 填写规则 |
| --- | --- |
| `evidenceKind` | `owner-confirmed`：相关事实由用户确认；`public-observation`：有实际核对的公开来源；`approved-baseline`：仅迁移既有已验收内容，不能用于绕过新作品核对 |
| `publicationStatus` | 当前检查接受 `public`。根据实际依据登记，不因准备加到网站就将状态改成 public |
| `scope` | `{ "kind": "work", "id": "该作品 ID" }`；资料必须支持该作品，不能借另一场活动或全品牌原则补事实 |
| `asOf` | 依据适用的确认／观察日期，格式 YYYY-MM-DD；不是编辑 JSON 的日期，也不表示本轮重新检查过链接 |
| `sources`、`basis` | HTTPS 公开来源，包含当前作品主链接；简述哪些事实得到支持，不复制私聊 |
| `reviewNotes` | 尚待核对的字段和问题；无已登记问题时为 `[]`，不等于所有事实都已独立验证 |

`harness/evidence.mjs` 校验上述声明的结构、允许值、合法日历日期和作品链接对应关系。它**不会**打开链接、判断授权真伪、核查证据时效或未来日期，也不会从文案中识别所有虚构事实。公开视频不等于获准新增官网记录；用户的更新范围与素材使用权限仍须人工确认。若用户明确授权使用 unlisted 素材，应按该实际状态补充有针对性的流程与测试，而不是谎报 public；现有规则不是永久禁止这种发布方式。

被标记为历史设想、分析、非公开或其他作品的资料会被拒绝。`reviewNotes` 则只输出 **MANUAL REVIEW** 提醒，不阻断测试：通过不等于这些问题已解决。修改相关字段或复用相关声明前核实，并在交付说明中披露仍相关的未决项；无关的维护不自动改写公共文案。当前已登记 Session 003 的日期语义，以及“Dublin's first Yunnan menu”的宣传性首份声明。

完整历史保留在用户原始资料中，可选本机定位为 Git 忽略的 `docs/design/history-reference-index.md`。版本化资料只保存必要的原则摘要与公开来源。档案中的 S12 等派生维护材料可以说明整理过程，不能循环引用为新的独立原始确认；原始来源不可读时明确说明。

## 3. 做一次编辑选择

作品分类以实际内容为准。一段在餐厅录制的 DJ Set 可以成为 Session；是否同时属于公开 Experience，需要有实际活动依据。Studio 的选择看视觉作品本身。不要为填满分类而把同一段事实包装成多个项目。

新公开视频、系列名或上传顺序不自动决定网站分类和 Session 编号。先确认它属于现有系列、独立作品还是别的记录；不要根据现有条数自行补成下一号。作品中使用某位艺人的曲目，也不能据此写成艺人到场或正式合作。

首页保留一项主推和少量精选。加入新内容时，明确哪项被主推、哪些旧作继续精选、哪些只进入 Archive。作品多起来时先换精选位，不持续加长首页。完整作品和真实历史信息应可在 Archive 找到。

更新中检查这些关联：

| 来源 | 要检查的去处 |
| --- | --- |
| Session | 首页主推／精选、Club、Archive、Studio 选择、视频与图片 Sitemap、VideoObject |
| Experience | 首页精选、Club、Archive、图片 Sitemap、活动地点与日期 |
| 成员／联系方式 | About、首页人物入口、Contact、页脚、组织结构化信息 |
| 标题／文案 | EN／ZH、桌面／手机、独立卡片与首页精简版本 |
| 新页面／分类 | 主导航、首页目录、语言切换、canonical／hreflang、Sitemap |

开始编辑前看当前数据结构和消费位置。`src/data/site.ts` 是现行主要内容入口，旧 `artists.ts`、`works.ts` 和旧翻译说明不能作为新流程的依据。以下字段是当前的编辑入口：

| 编辑意图 | 更新位置 |
| --- | --- |
| 增加作品及通用卡片说明 | `sessions` 中的记录，填写双语 `description` 及媒体事实 |
| 为首页主推准备专用标题与简介 | 该 Session 的 `homeFeature.title`、`homeFeature.body`，各自包含 EN／ZH |
| 选择首页主推 | `editorialSelection.home.featuredSessionId` |
| 选择首页其他精选并确定顺序 | `editorialSelection.home.selectedSessionIds` |
| 选择首页 Experience | `editorialSelection.home.featuredExperienceId` |
| 为首页 Experience 准备专用标题与简介 | 该 Experience 的 `homeFeature.title`、`homeFeature.body`，各自包含 EN／ZH |
| 选择 Studio 作品及顺序 | `editorialSelection.studio.sessionIds` |
| 调整“最新 Session”等通用标签 | `siteCopy` 对应语言的 `home.featureLabel` |

页面通过 `getHomeSelection()` 和 `getStudioSessions()` 读取选择。新作品入库不会自动更换首页或 Studio；要主推时同时填写 `homeFeature` 并更新引用，不再另写一份带旧编号的首页文案。检查引用有效、没有重复、首页主推未在其他精选位再次出现。

## 4. 实施并保持公共表达清楚

内容、图片和元信息尽量从同一记录读取；避免在多个页面分别手写日期、视频编号或主推标题。新增字段要带中英文完整定义，不在缺翻译时默默回退成另一语言。

保持已确认的字体、颜色和布局分工。若新文案过长，先检查短句组织、局部行宽与字号。不要用 `overflow-x: hidden` 隐藏真实溢出，也不要为首页一个重复问题删除所有页面的卡片信息。

图片保存为稳定本地素材，确认能被公开请求。核对真实场地与裁切，而不是只看文件存在。新活动在都柏林之外时，检查卡片、JSON-LD 和图片说明中是否仍写死 Dublin／IE。

搜索信息描述真实可见内容。canonical 与语言链接沿用网站配置；不要为某次视频更新更换整个站点的分享主图或组织定位。

## 5. 自动检查与可查看报告

```sh
# 快速内容、代码、类型检查
npm run check

# 完整生产构建与浏览器检查
npm run verify

# 查看浏览器报告与截图附件
npm run report
```

单独定位问题可运行 `npm run test:content`、`npm run test:browser`。最终结论以本次实际输出为准，不能沿用上次“全部通过”。完整验证复制当前项目到临时目录，复用 `node_modules` 的链接，在自己的 `127.0.0.1:3107` 服务上测试并清理。它不覆盖当前项目的 `.next`，也不停止用户正在使用的预览服务；不要为验证再留下几个常驻开发服务。

浏览器报告在 `artifacts/harness/report`。报告中的截图是审阅证据，不自动代表审美验收。构建失败、浏览器不可用或外部网络受限时，记录具体未完成项；只有实际完成的检查才能写“通过”。

测试失败应先查是否出现真实回退，再判断测试是否需要随已确认的新设计更新。不能只为让结果变绿而删除检查或无说明地替换基线。

## 6. 人工视觉与交互审阅

完整验证关注 **320、390、760、1040、1041、1280、1440、1920px**，覆盖窄手机、手机、关键布局断点的两侧和大屏。受影响页面必须同时看 EN 和 ZH。移动端模拟与真实手机触摸分别标明；截图不能证明拖动手感。

| 观察对象 | 判断依据 | 应留下的证据 |
| --- | --- | --- |
| 重点与气质 | 作品是否先被看到，界面是否仍有纸色、墨黑与真实现场的关系 | 变更区块截图与一条具体判断 |
| 字体与断行 | 长标题不挤、不拆坏短句；三个中文词的标点间距协调 | 中英文桌面／手机截图；样式改动附同视口前后图 |
| 留白与对齐 | 组内紧密、组间有停顿；左右栏重心与下一章节衔接自然 | 需要时包含相邻区块，避免只截一小段 |
| 素材 | 没有破图、拉伸、关键人物或封面文字误裁 | 实际渲染图，不只检查原图 |
| 文案 | 人、地点、作品类型可理解；氛围有具体事实支撑 | 相关中英文成对审阅，说明改写理由 |
| 内容覆盖 | 首页不重复，旧作仍在 Archive，社媒／成员未丢失 | 浏览器结果或记录列表 |
| 导航与动效 | 目录目标正确、语言切换保留位置语境、键盘可用、触摸不阻止滚动 | 测试结果；涉及手感时补真实设备观察 |
| 减少动态效果 | 无强制扫描演示，核心信息可理解 | 该偏好下的检查记录 |

每次至少回答：新内容把视线带向哪里？哪一处断行或留白决定了阅读节奏？为什么这种呈现适合这个作品？用证据与理由回答，不给“高级感 95 分”一类分数。

设计工具或 Stitch 可以提供构图建议，但建议必须落到实际页面和截图上审阅；工具推荐本身不构成 NeoBee 的新方向。

### 用不同类型的更新检验原则

下表用于人工演练，避免规范只记住上一轮错误；它不是已经接入的语义测试。

| 情况 | 应如何判断 |
| --- | --- |
| 连续新增几场餐厅录制 | 可以精选，但不能把整个品牌改成餐饮活动品牌（B01） |
| 新增更强烈的 techno／实验作品 | 看作品与实际场景；不以页面安静或 YiBU 要求排除（B04） |
| Studio 出现非音乐主题的摄影委托 | 可以符合视觉分支；整体音乐主导不等于每件作品必须同题（B01） |
| 作品在 Dublin 以外，或没有亚洲音乐线索 | 根据真实地点与内容介绍，不强补地域标签（B02） |
| 为了专业形象改写 About | 用真实作品与职责支撑，不编团队规模、稳定客户或合作实绩（B03） |
| 品牌封面压过了个人署名 | 保持团体呈现，也保留清楚、准确的表演／制作贡献（B05） |
| 发现更早的炫目视觉提案 | 视为历史方案，不能拼回当前视觉；新方向另行确认（V01） |

## 7. 交付记录模板

把下面的信息放进交付消息或变更说明。按实际工作量缩短，不用凑满每个栏目；未检查项不能省略成“都好”。

```text
本次更新：
类型：内容更新 / 局部呈现 / 设计变化
涉及页面与语言：

内容与事实：
- 新增/修正了什么；公共来源或用户已确认事实。
- 依据属于直接确认 / 公开观察 / 历史设想 / 维护性归纳；适用于哪件作品或哪层规则。
- 本次相关决策 ID（B01–B05 / V01）及具体判断，不必逐条凑齐。
- 主推与精选如何选择，旧作在哪里继续保留。

视觉判断：
- 视觉重点、标题断行、留白/裁切各有什么具体变化。
- 为什么符合当前 NeoBee 方向。
- 如改变字体/颜色/结构/动效：原方案 → 新方案，理由是什么。

证据：
- 本次运行的命令与真实结果。
- 查看过的页面、语言、视口；真实手机是否检查。
- 报告位置与前后截图附件。
- 未完成检查、缺失资料或仍待判断的地方。
- 与本次有关的 MANUAL REVIEW 提醒，是否核实、还有什么未解决。

发布状态：仅本地 / 已提交 / 已推送 main / 已确认线上部署。
如更新视觉参照：参照提交、确认日期、决定及理由。
```

## 8. 发布与后续维护

用户要求推送时，完成必要检查并沿现有 `main` → Vercel 自动部署流程发布。确认实际提交与远端状态；只有观察到部署状态或线上页面后才说“已部署”。推送成功和部署成功是不同证据。

发布后针对本次影响检查线上关键页面与链接，不必把所有测试无理由重跑。发现回退时保留现象与证据，再修复对应问题。

新的品牌或交互方向获确认后，更新 [品牌与视觉系统](brand-system.md) 及 [决策记录](decision-register.md) 中的对应条目和参照说明。保留确认日期、范围、替代关系和“为什么改”的短记录，让下一次更新能理解选择，而不只继承一组数值。
